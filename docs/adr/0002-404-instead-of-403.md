# ADR 0002: Return 404, not 403, when a user has no access to a board

Status: Accepted  
Date: 2026-10-22 (written after the decision, see README)  
Related commits: `d2e4523`, `0de4d1d`, `111cd25`, `a45c2c7`

## Context

Boards have numeric IDs. If the API answers "403 Forbidden" for a board the
user cannot see, the user learns that this board exists. An attacker could
try many IDs and find out which boards exist and how many there are.

## Decision

If a logged-in user has no access to a board at all, the API returns
`404 Not Found` with the same message as for a board that does not exist
(`get_board_or_404` in `permissions.py`). An invalid ID also returns 404,
not 500.

The same rule applies to everything that belongs to a board (tasks,
columns, labels, comments, attachments and so on): the view loads the
object, then checks access to its board, and answers 404 if there is none.
The access check must come before the edit check, otherwise a user
without access gets 403 and learns that the object exists. Commit
`111cd25` fixed five endpoints that had this order wrong (task reorder,
task duplicate, column reorder, webhook detail, webhook deliveries), and
`a45c2c7` three more (template edit, task from template, subtask reorder).

The same applies to IDs that point to other objects. A dependency target
on a board the user cannot see gets the same 404 as a task that does not
exist. Teams and users follow the rule too: assigning a board to a team
the user is not part of answers like a missing team, and editing or
deleting a user who shares no board with the actor answers like a
missing user (`a45c2c7`).

The real rule is "the same answer as for an object that does not exist".
Usually that is 404. Column reorder takes a list of IDs and already
answered 400 "Some columns not found." for unknown IDs, so columns on
foreign boards get exactly that answer too.

This rule is only for users **without any access**. A board member who may
read but not edit (for example a viewer) gets `403 Forbidden` on write
requests. This user already knows the board exists, so 403 leaks nothing
and gives a clearer error.

## Consequences

- The existence of private boards is not leaked.
- Debugging is harder: "does not exist" and "no access" look the same for
  the client.
- The frontend cannot show a message like "ask the owner for access",
  because it does not know that the board exists.

## Alternatives considered

- **403 with a generic message:** easier to debug, but it still leaks that
  the board exists.
- **UUIDs instead of numeric IDs:** makes guessing hard, but it is a bigger
  change to the data model and does not solve the problem on its own.
